## cheng2024draco — Dataflow-Guided Retrieval Augmentation for Repository-Level Code Completion

*(Cheng, Wu, Hu; ACL 2024; arXiv 2405.19782. Detail below confirmed from the arXiv HTML full text; result tables transcribed from the HTML render — treat exact digits as high-confidence-but-re-checkable.)*

### What the paper actually does

**Problem framing.** Code LMs fail on private-repo completions because the needed definitions live in other files. Prior cross-file retrieval keys on either (a) *import relations* (pull everything a file imports) or (b) *text similarity* (RepoCoder/RG-style: retrieve code chunks similar to the unfinished context). The authors' thesis is that both are "insufficiently relevant to the completion target" — imports over-fetch, similarity retrieval fetches lexically-near but semantically-irrelevant code.

**Method — DraCo (Dataflow-guided Retrieval augmentation for Code completion).** Two phases:

1. *Offline indexing → repo-specific context graph.* Parse every Python file with **tree-sitter** (chosen because it tolerates incomplete/uncompilable snippets). Traverse the AST to collect four **code-entity node types**: Module (file path + docstring), Class (name/signature/docstring/start-line), Function (name/signature/docstring/body/start-line), Variable (name/statement/start-line). Two **edge types** wire them: *contains* (natural containment: a class contains its methods) and *depends*. The *depends* edges come from an **extended dataflow analysis**: the authors take a standard dataflow graph but keep only five **type-sensitive relations** that tell you *what a variable is or where it derives from* — `assigns` (`v=u`), `as` (`with f() as v`), `refers` (`u.v`), `typeof` (type hints `-> v`), `inherits` (`class v(u)`). Type-*insensitive* dataflow (e.g. a plain string parameter) is pruned. Cross-module *depends* edges are formed by linking variables in local import statements to the entities they point at in other files. The result is a heterogeneous directed graph G = {(h, r, t)}.

2. *Online retrieval at the cursor.* Run the same dataflow analysis on the *unfinished* file to get fine-grained import info of the form `(module, name)` (and `(module, name.attr)` expanded via `refers`). Map that to a graph node — resolve the module via directory structure, then locate the entity inside by string match. Then **retrieve along `depends` edges via depth-first search**. Entities with a data-relation to the *target line* form a primary set `E_r`; other imported entities `E_o` are appended until a token budget is hit (Algorithm 1, `Generate_BK`, protects `E_r` from truncation). Algorithm 2 (`Organize_BK`) groups by module, merges `contains`-related entities, sorts within-module by line number, and orders modules by a **pseudo-topological sort** with two priorities: dependencies first (programming convention) and `E_r`-reachable modules ahead of `E_o` (a "lost-in-the-middle" placement heuristic). Background knowledge is wrapped as a leading multi-line string, each block prefixed with a `# file path` comment, then the unfinished code. Context budget uses the RLPG-style dynamic allocation (half BK / half code, unused reallocated). Two prompt **scopes**: *definition* (signatures only) and *complete* (adds bodies + variable statements).

**Setup & scale.** Purely *inference-time, training-free* — DraCo never updates model weights; it only constructs prompts. Evaluated on eight code LMs: CodeGen-{350M, 2.7B, 6.1B, 16.1B} (2K ctx), CodeGen2.5-7B, SantaCoder-1.1B (2K), StarCoder-15.5B (8K), Code Llama-7B-Python (≤8K), plus GPT-3.5 and GPT-4 on a 50-example sample. Two Python benchmarks: **CrossCodeEval** (Python subset; 471 repos, 2,665 examples, cursor always at a `.`) and their new **ReccEval** (2,635 repos, 6,461 examples, cursor at *any* token — more diverse targets). Baselines: Zero-Shot (in-file only), CCFinder-1/-2 (import-based cross-file finders — DraCo's "import relation" foil), RG-1 (single-pass similarity retrieval = RepoCoder iteration 1), and **RepoCoder** (iterative retrieve-generate, the SOTA foil). RLPG/RepoFusion are *excluded because they require training*.

**Headline numbers.** Averaged over models, DraCo beats RepoCoder by **EM +3.43%, ES +1.00%, ID-EM +3.62%, identifier-F1 +3.27%**, at **~100× lower prompt-construction latency** (DraCo ~40 ms vs RepoCoder ~4,000 ms; RepoCoder is slow because it runs the model to generate a draft, then re-retrieves). Concrete points: CrossCodeEval StarCoder-15.5B EM 29.12 (RepoCoder) → **34.67** (DraCo); SantaCoder-1.1B 13.62 → **20.64**. ReccEval StarCoder-15.5B EM 46.26 → **46.49** (marginal), SantaCoder 27.29 → **30.26**. The one loss: CodeGen-350M on ReccEval, where DraCo (22.12 EM) trails RepoCoder (22.46) on code-match metrics but leads on identifier metrics (ID-EM 29.73 vs 29.05, F1 46.09 vs 43.91). **Ablations** (Table 6): removing cross-file depends, removing intra-file dataflow (→ coarse line-order import info), and removing dataflow entirely all hurt monotonically; *w/o dataflow* is the worst but *still ≈ CCFinder* because the prompt is better-formed. The *complete* scope always wins. A revealing Code-Llama finding (Fig. 4): as max input grows 2K→8K, DraCo *helps StarCoder more but helps Code-Llama less* — a code-specialized LM exploits the retrieved dependencies better than a further-trained general LM.

### Methodology: theirs vs. ours

**The shared idea, stated precisely.** Both DraCo and TS2TS say: *the import/dependency graph tells you which distant code a completion needs, and generic proximity (concatenation order, text similarity) is a poor substitute.* DraCo is explicitly flagged in our related-work notes (`related_work_notes.md` §5, and `code_briefs/eval_harness.md`→lit implications) as **the closest inference-time analog to our import graph**. Both use `tree-sitter` to extract code structure without requiring compilable code (DraCo for its whole pipeline; ours in `model/graph_traversal/*` link detectors and the Tier-1 oracle, `code_briefs/link_detectors.md`).

**The dividing axis — train-on-structure vs. retrieve-at-inference.** This is the whole contrast:

- *DraCo = pure inference-time prompt assembly.* The model is frozen. The graph is built per-repo at index time and queried per-cursor; its only actuator is *token order inside the prompt* fed to an off-the-shelf causal LM under ordinary dense causal attention. There is no attention-level edge and no gradient ever flows through the graph. Their `pseudo-topological sort` (dependencies-first module ordering) is, notably, *exactly the DeepSeek-Coder import-topological-sort idea (`guo2024deepseekcoder`) applied at inference instead of pretraining* — a nice triangulation point.
- *TS2TS = the graph edge is trained into attention.* Our import edge is a hard, binary, block-sparse **attention grant** (`CrossDocLinkMaskCreator`) used *identically in pretraining and inference* — the "train/inference mirror" that `code_briefs/generation_retrieval.md` calls our strongest claim (shared `LinkDetector` protocol, shared `index_doc_span` match key, shared grant geometry from `link_end_pos` onward, shared DAG ordering). Where DraCo *orders* the fetched entity earlier in a flat prompt, we *materialize* the fetched doc as a first-class `DocSpan` and open an attention edge to it (`_handle_link` inserts the target physically before the linker so the cross-doc mask can grant attention — retrieval **by insertion into the packed sequence**, not context-string concat).

**Edge type.** DraCo's edge is a *prompt-ordering + selection* edge (which entities enter, in what order). Ours is an *attention* edge. Neither is a GNN message-passing edge, a cached-KV store, nor a training-pair contrastive signal — but they sit on opposite sides of the "does the model learn to use the edge" line. Our `code_briefs/generation_retrieval.md` KV-cache note is relevant here: *neither* system reuses KV (DraCo re-prompts a frozen model each cursor; we full-recompute each token), but DraCo at least gets standard incremental decoding of its assembled prompt, whereas our insert/evict + pure-RoPE design forbids KV reuse by construction.

**Retrieval precision — the sharpest methodological convergence.** DraCo's core empirical claim is that *dataflow-typed* dependency retrieval beats both raw-import retrieval (CCFinder) and text-similarity retrieval (RepoCoder). Our `precise` matching in `score_completion_with_context_docs` (per-import-path → doc_id resolution, `code_briefs/eval_harness.md`:14) and our `_resolve_target` 3-tier cascade (`document_corpus.py`) are doing the *same job* — resolving a specific symbol to a specific target — but deterministically via identifier normalization (`link_detectors.md` §"Identifier normalization"), not via a learned dataflow graph. DraCo's `refers`-expansion (`(module, name.attr)`) is finer-grained than our path→doc resolution: it retrieves the *specific attribute/method's* definition, whereas our unit of retrieval is the whole target document (optionally head-truncated to abstract+intro via `max_corpus_doc_tokens`). **DraCo retrieves sub-document entities; we retrieve documents.** That granularity gap is worth naming in the paper.

**What they share with us and where they diverge, in one line each.** Share: import graph as the relevance signal; tree-sitter structural extraction; dependency-topological ordering (their pseudo-topo sort ≈ DeepSeek-Coder ≈ our DAG target-before-link). Diverge: frozen model + prompt assembly (theirs) vs. trained attention grant reused at inference (ours); entity-granular retrieval (theirs) vs. document-granular insertion (ours); dataflow-typed edges (theirs) vs. syntactic import/hyperlink/citation edges (ours, no dataflow typing); Python-only static analysis (theirs) vs. 11-language composite detector (ours).

### Predictions & open questions for our method

- **Dataflow-typing predicts *where* our cross-doc effect is real vs. noise.** DraCo's central result — typed dataflow beats raw import (`w/o dataflow` ablation drops StarCoder EM 34.67→28.82) — predicts that **not every import edge we train/grant carries usable signal**. Our PythonImportDetector emits *candidate file paths* for every import (`link_detectors.md`:49, "candidate over-generation"), including imports whose symbols are never used near the completion. DraCo's evidence says the *type-insensitive* fraction of those edges is close to dead weight. Prediction: our per-token Δnll gain should concentrate on completions that actually *use* an imported symbol — which is exactly what our `use_line` scope isolates (`benchmark_harness/scopes.py`, `eval_harness.md`:25). We should *expect the native→use_line flip* (go/java ~0 → clearly positive) to look like DraCo's zero-shot→DraCo jump, and we should *expect diminishing returns from granting attention to imported-but-unused targets* — a candidate ablation: restrict grants to imports whose symbol appears in the completion window.

- **Model-capability interaction predicts our undertraining sensitivity.** DraCo's Code-Llama-vs-StarCoder finding (a *code-specialized* model exploits retrieved dependencies; a general model further-trained on code does not, and *degrades* as context grows) is a direct warning for our undertrained/small-model runs. Our eval harness already logs the failure (`eval_harness.md`:53, "zig 59M neg", "underpowered/undertrained pervasive"). Prediction: the cross-doc attention edge will *hurt* on models too small/undertrained to use the fetched content — the benefit is gated on the base model's competence, and our compute-control (concat) arms may look *better* than the cross-doc arm precisely where the model is weakest. This reframes negative results as expected, not damning.

- **Their 2K-context wins are our long-context stress test.** DraCo shows big gains even on CodeGen-350M at *2K* context — because tight, precisely-retrieved context beats a long dump. Our system operates at 32k and *inserts whole documents*. Prediction: our advantage over DraCo should be strongest when the needed context is *large and multi-hop* (a target doc that itself links onward — our `max_link_depth` recursion, which DraCo has no analog for; DraCo does a single DFS over a precomputed graph, not recursive fetch-and-read). Where a single small definition suffices, DraCo's precise entity-slice is likely *more token-efficient* than our whole-doc insertion. This is a real efficiency concession to preempt.

- **Open question DraCo can resolve for us:** *is the gain from the right code or from any extra plausible code?* DraCo's `w/o dataflow` ablation is the closest external analog to our **derangement placebo** (`eval_harness.md`:28) — it swaps precise retrieval for coarse import retrieval and still keeps *some* signal, showing the benefit is partly "better-formed prompt" and partly "right content." This validates our placebo design and suggests we report a *coarse-import* arm (grant attention to *all* imported docs, not the resolved one) as an intermediate control between placebo and precise, mirroring DraCo's CCFinder-vs-DraCo gap.

- **Open question we might resolve for them:** DraCo cannot handle completions where "code intent is unclear" — new-line or function-body starts where there is no import to key on (their stated limitation). Our system fetches on *generated* links during decoding (a produced import/citation/link triggers a fetch, `generation_loop.py`), so we retrieve based on what the model *decides to write*, not only on what is already imported above the cursor. Our recursive `corpus_then_generate` fallback even synthesizes an absent target. That is a genuine capability DraCo lacks.

### Gotchas

- **Cursor position defines the benchmark, and it is easy to game.** CrossCodeEval always cuts the cursor at a `.` (member-access) — the single most import-dependent position, where any cross-file method has maximum leverage. DraCo built ReccEval specifically because "last char = dot" over-states cross-file benefit; ReccEval cuts at *any* token and DraCo's margins shrink sharply (StarCoder EM +5.55 on CrossCodeEval vs +0.23 on ReccEval). **Direct warning for us:** our `use_line`/`native` scopes and our firing-conditioned subset selection (`eval_harness.md`:48, reviewer-attackable #2) risk the same artifact — we choose the examples where the edge *can* fire, which correlates with clean parseable imports and member-access-heavy lines. DraCo's own diagnosis is that this inflates the effect; we should report an "any-token / unconditioned" arm as they did.

- **Decontamination by release date is the credible move.** DraCo dated ReccEval repos to PyPI releases *after* the pretraining corpora (2023-01-01 to 2023-04-28) and *filtered out* examples StarCoderBase-1B already solved exactly. They still flag residual leakage risk for Code-Llama/GPT (unknown training cutoffs). This is exactly our HotpotQA-2017-leakage concern (`eval_harness.md`:53 #5) and our SHA1/repo-name dedup. Lesson: date-based decontamination + "remove what the base model already gets right" is a cleaner story than n-gram dedup alone; consider adopting the "filter examples the base model solves" trick to harden our fired subset.

- **RepoCoder's cost is the honest baseline framing.** DraCo's 100× latency win comes because RepoCoder runs the model twice (draft → re-retrieve). Our system is *also* expensive (full O(T²) recompute per token, no KV cache — `generation_retrieval.md`:38), so we cannot claim DraCo's efficiency advantage; if anything DraCo is the efficiency yardstick we lose to at inference. Frame our cost honestly against DraCo, not against RepoCoder.

- **Metric choice: they report EM/ES/ID-EM/F1 on generated text; we report Δnll.** DraCo's identifier-F1 gains (+3.27) are larger and more stable than raw EM, precisely because EM is brittle. This supports our preference for continuous Δnll (`eval_harness.md`, `schaeffer2023mirage`/`biderman2024lessons` in notes) but also means our results are *not directly comparable* to DraCo's table — a reviewer will ask for a generation-metric bridge. Our `annotated`/`experimental` conditions and RepoBench port are the place to produce one.

- **Dataflow is Python-only and hand-built.** DraCo lists language portability as a limitation — every new language needs its dataflow analysis re-extended. Our syntactic import/link detectors already span 11 languages (`link_detectors.md`) *without* dataflow typing — cheaper to port but coarser. The trap for us is the mirror image: our Java source-root ambiguity, Python candidate over-generation, and markdown-token-id hardcoding (`link_detectors.md` reviewer-attackable) are the price of skipping real static analysis. If a reviewer cites DraCo to demand typed dataflow, our answer is scale/multilinguality + the trained edge, not per-language precision.
