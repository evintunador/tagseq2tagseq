## What the paper actually does

RepoBench is a **benchmark suite**, not a model. It targets *repository-level* next-line code completion, where the token/line to be predicted depends on code that lives in **other files** of the same repo (an imported helper, a sibling class, a cross-module API). It decomposes the problem into three linked tasks:

**RepoBench-R (Retrieval).** Given the in-file context and a pool of candidate cross-file code snippets, rank/retrieve the snippet(s) that actually contain the needed cross-file context. Metric: **acc@k** (accuracy that a gold snippet appears in the top-k). Two difficulty tiers by candidate-pool size: **Easy** = 5–9 candidates (reports acc@1, acc@3); **Hard** = 10+ candidates (acc@1, acc@3, acc@5). Findings: dense **UniXcoder consistently beats** other retrievers; lexical **Jaccard beats Edit-Similarity**; Python retrieval scores higher than Java.

**RepoBench-C (Completion).** Given in-file context (import statements + preceding lines, capped ~30 lines) **plus** cross-file context (retrieved snippets, inserted as commented code), predict the **next line**. Metrics: **Exact Match (EM)** and **Edit Similarity (ES = 1 − Lev/maxlen)**. Two length buckets: **RepoBench-C-2k** (prompts ≤ ~1,925 tokens) and **RepoBench-C-8k** (≤ ~7,685 tokens). This is the task OUR harness ports.

**RepoBench-P (Pipeline).** End-to-end: retrieve, then complete, on long repo contexts (min token thresholds ~12k Python / 24k Java, ≥10 candidates). Metrics EM/ES "in line with RepoBench-C." (The ar5iv text I read reports **EM/ES only for -P; I did not find CodeBLEU** there — do not attribute CodeBLEU to RepoBench without checking the PDF.) Finding: cross-file context helps even when retrieval is imperfect; better retrieval and placing similar snippets **nearer the target line** both help (a lost-in-the-middle signal).

**The three settings (the axis that matters to us).** For -R and -C each example is one of:
- **Cross-File-First (XF-F):** mask the **first** appearance in the file of a line that uses cross-file context — so there is **no prior in-file usage** to lean on; the model *must* use long-range cross-file context. This is the hardest setting **and the one our port uses**.
- **Cross-File-Random (XF-R):** mask a random, non-first occurrence — earlier in-file usage can leak the answer.
- **In-File (IF):** no cross-file dependency.

**Data / leakage control.** Test repos are the most recent **non-forked, permissively-licensed** GitHub repos (crawled via the GitHub API), created **after 2023-02-09** (aligned to The Stack cutoff) and **before 2023-08-03** — a *temporal* decontamination against models trained on the github-code / CodeParrot dump (cutoff 2022-03-16). The text emphasizes non-forked + license filtering; I did **not** see an explicit hash-based dedup step described. Historical repo counts: 10,345 Python / 14,956 Java; test repos 1,075 Python / 594 Java. Task instances are large (e.g. RepoBench-R Easy XF-F = 12,000 per language).

**Models evaluated.** Codex (`code-davinci-002`, 175B), CodeGen (350M–16.1B), StarCoder/StarCoderBase (15.5B); retrievers CodeBERT, UniXcoder, plus lexical Jaccard/Edit. Headline: models are close on Python-2k but Codex clearly leads on Java, and the completion gap **widens at 8k** — longer cross-file context is where the systems separate.

## Methodology: theirs vs. ours

RepoBench is our **headline code benchmark**, but our harness does **not** run RepoBench's own task. It **repurposes the XF-F completion data** into a paired contrastive perplexity experiment. The differences are on the eval-methodology axis, exactly as the brief asks:

**1. Generative EM/ES → paired teacher-forced Δnll.** RepoBench scores a *generated* next line by string match (EM) or edit distance (ES). Our harness (`run_repobench_cross_doc`, `nlp_benchmarks.py:987`) never generates: it teacher-forces the gold `next_line` and takes **mean NLL** over the completion tokens from `log_softmax(forward_inference logits)` (logit@t predicts token@t+1, per `eval_harness.md`). The **headline is the paired contrast** Δnll = flat_nll − cross_nll on the *same* completion tokens:
- **cross arm:** cross-file snippets packed as leading aux `DocSpan`s, then `import_statement + "\n" + cropped_code` as primary context, then `"\n" + next_line` as completion; the import detector fires on the flat sequence and grants the primary doc read-access to the specific imported snippet via `forward_inference(mask_type='cross_doc_link')` (`score_completion_with_context_docs`, `scoring.py:617`).
- **flat arm:** the identical `(context, completion)` pair scored under `doc_causal` with **no aux** (`score_completions_independent_batched`), batched.
- Δ is computed only over the **paired FIRED subset** (`n_cross_doc` — examples where an import actually resolved to an aux snippet); non-firing examples fall back to flat and appear only in the `with_fallback` figure.

Why this repurposing is defensible: the two arms score **identical text at a single tokenization point**, so **memorization/contamination cancels** in the difference (RepoBench's temporal cutoff is a coarser, absolute control; ours is a *relative* control that survives leakage). Token-accounting parity is enforced at the tokenization boundary (`schema.py`, Tier-0 re-check).

**2. Precise, deterministic import→doc resolution vs. RepoBench's retrieval.** RepoBench-R is an entire *task* about retrieving the right snippet (fuzzy, learned/lexical). Our port sidesteps retrieval: `_repobench_aux_identifier` (`nlp_benchmarks.py:965`) shapes each aux snippet's `raw_identifier` so the language's `index_doc_span` yields **exactly** the key the import detector emits — for Python the snippet path verbatim (`repo:pkg/mod.py`); for Java the FQN recovered from the path by stripping a build **source root** (`src/main/java/`, etc. — `_strip_java_source_root`, `_JAVA_SOURCE_ROOTS`) so `com/foo/Bar.java` dotifies back to `com.foo.Bar`. Matching is an **exact hashmap lookup**, not ANN/BM25. So we effectively hand our model the *gold retrieval* and measure only whether the trained cross-doc **attention edge** exploits it. This is the deterministic analog of RepoBench-R's oracle.

**3. Train/inference symmetry.** The `cross_doc_link` mask + detector + match-key used here are the **same machinery used in pretraining** (packing graph-close docs into 32k, granting a linker read-access into its target from the link position onward — `masks.md`, CLAUDE.md). RepoBench's baselines are all frozen off-the-shelf LMs prompted with concatenated snippets; the structure is never trained in. Our port is the eval face of a *trained* edge.

**4. `cross_file_first` maps cleanly onto our design — and drives the `use_line` scope.** XF-F masks the **first** cross-file use line, so the target line *is* the first site where an imported symbol is used. That is precisely where a cross-doc attention grant should pay off. The port loads `split="cross_file_first"` (`ports/repobench.py:19`), builds `context = import_statement + "\n" + cropped_code`, `target = "\n" + next_line`, and — importantly — sets `full_file = context + target`. RepoBench ships only context-up-to-hole plus the single `next_line` (`all_code` is just a license header, **not** the full file), so there is **no file content after the target**. Consequence documented in the port: the use-scopes **collapse to `use_line` here**, because RepoBench's `next_line` already *is* the first cross-file use line by construction. So on RepoBench, `use_line` should **reproduce native** — which is exactly the *validation* the harness wants (RepoBench is the "CALIBRATION REFERENCE" defining the legitimacy band new ports are judged against).

**5. How `use_line` re-anchors scoring (general mechanism, `scopes.py`).** The scope machinery matters more for *other* ports (ASE-Kotlin, CrossCodeEval) whose FIM targets are arbitrary spans that may not touch any imported symbol — a candidate cause of the Kotlin Tier-2 miss. `use_line` re-anchors the scored region to a genuine **use site**, decided **without parsing import syntax**: it takes the set of **top-level names DECLARED in the granted aux docs** (tree-sitter `_DECL_NODE_TYPES` per language) and finds the first completion-region line whose identifiers intersect that set (`_aux_declared_names` + `_identifier_lines`, `scopes.py:83–221`). For non-native scopes the **context is rebuilt as the full-file prefix up to the use site**, so `use_line`/`use_block`/`rest_of_doc` share identical context and vary only target width — a clean ablation of *where the cross-doc signal lives*. This sidesteps `import *` (a star import's names are exactly the aux declarations) and needs only a top-level-declaration query, not a full import grammar. The compelling result the brief flags is the **native→use_line flip** (go/java ~0 or negative under native → clearly positive under use_line) — cross-doc benefit is real but concentrated at the use line, invisible when you average over an arbitrary span. RepoBench, by construction, is the one benchmark where that flip is a no-op, which is why it anchors the calibration.

## Predictions & open questions for our method

- **The XF-F↔use_line correspondence predicts our effect is largest exactly at first-use lines.** RepoBench's own design decision — that XF-F is the hard, cross-file-mandatory setting — is evidence that the informative signal concentrates at the first use of a cross-file symbol. Our use_line re-anchoring operationalizes the same intuition. Prediction: our cross-doc Δnll should be **strongest on first-use lines** and **decay** as we widen to use_block/rest_of_doc (later lines re-use symbols the in-file prefix already introduced), and near-zero where the completion never names an imported symbol.

- **8k-widening predicts our advantage grows with cross-file distance.** RepoBench's completion gap widens from 2k→8k. Our 32k packing is built precisely for the long-range regime; expect the cross-vs-flat Δnll to **increase with the amount of interposed context** between the grant point and the use site — a favorable, testable slice. (Caveat: this is also where our own config-mismatch bugs bite — see Gotchas.)

- **Retrieval quality dominates — and our placebo answers a question RepoBench leaves open.** RepoBench-P shows better retrieval → better completion, but its pipeline can never separate "the *right* snippet" from "*any* extra plausible in-language tokens," because both retrieval and completion vary together. Our **derangement placebo** (`tier2.py:169–234`) does exactly this: keep the example's own aux identifiers (so grants still fire, fire-rate preserved by construction) but swap in a donor's snippet *content* — attend to wrong-but-plausible code. If Δnll survives the placebo, the benefit is the *right imported code*, not extra tokens. This is our design **resolving** an ablation RepoBench cannot run. **But**: placebo is **Tier-2 only** — the headline RepoBench/HotpotQA runs have **no placebo arm** (the brief's #1 fairness gap).

- **Java should be the harder split for us too.** RepoBench finds Java retrieval and completion harder than Python, and our Java path has an extra failure surface: the FQN↔source-root reconstruction. Any repo whose layout lacks a known source root (`_JAVA_SOURCE_ROOTS`) yields a non-matching key → the example silently **falls back to flat** (no crash, but it drops out of `n_cross_doc`). Expect **lower fire-rate on Java** and a fire-rate that is itself layout-dependent.

## Gotchas

- **EM/ES penalize functionally-correct code; NLL avoids that but adds firing-conditioned selection.** We dodge the string-match artifact by using continuous NLL, but we introduce our own: Δ is measured **only over fired examples**, and firing correlates with parseable imports / recognizable layouts (`eval_harness.md` #2). Report `n_cross_doc`, fire-rate, and the `with_fallback` figure alongside the cross-only number; a headline Δ over a small, self-selected fired subset is attackable.

- **XF-F is the *hard* setting — good for a clean effect, but a biased sampler.** Because XF-F masks the *first* cross-file use, our fired subset is enriched for exactly the examples our mechanism helps. That is legitimate (it's what the mechanism is *for*), but it means our RepoBench number is **not** a general code-completion number; it is a targeted first-use-line contrast. State that framing explicitly.

- **The cross arm sees strictly more tokens than the flat arm (no placebo on the headline).** On RepoBench the flat arm has **no aux at all**, not wrong aux. So the headline Δ conflates "right imported code" with "any extra context." This is the single biggest reviewer target; the honest fix is to run the placebo (or at least a random-snippet control) on the headline RepoBench slice, not only Tier-2.

- **Temporal decontamination is coarse and now stale.** RepoBench's 2023-02-09→08-03 window protected 2022-era models; it is porous for any modern base model, and our own training corpus (The Stack / thestack) may overlap. Our SHA1 + repo-name dedup (`eval_harness.md`) is the stronger control, and the paired-Δ design cancels memorization — lean on those, don't cite RepoBench's cutoff as our contamination defense.

- **Config-mismatch bugs bite long-doc eval.** The brief records two that already fired on related cross-doc perplexity runs: the **32k→2048 budget bug** (`TS2TSModel` had no top-level `max_seq_len`, chain fell to a 2048 default and collapsed long-doc arxiv) and the **max_grants 64-vs-256 bug** (Python Δ moved 0.135→0.09). RepoBench-8k prompts reach ~7.7k tokens; if the eval budget silently truncates below that, the cross arm loses the very long-range context it is supposed to exploit and the effect vanishes for the wrong reason. Verify `backbone.max_seq_len` and `max_grants` before trusting any RepoBench-8k / cross-file-distance slice.

- **Java source-root stripping is heuristic and silent on failure.** `_strip_java_source_root` falls back to the path unchanged when no known root is present; the dotified key then just won't match and the example drops to flat with no error. A repo using a non-standard layout will quietly shrink the Java fired subset without any signal in the logs.

- **Don't tune scope/depth on the eval set.** The `use_line` re-anchoring is well-motivated a priori (it matches XF-F's construction), but presenting the native→use_line flip must be framed as *the mechanism finding its natural locus*, not as scope-shopping — otherwise it reads like the Option-B `span.start+1` key hack (`eval_harness.md` #3): looks like tuning until independently justified.
